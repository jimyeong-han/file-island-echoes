# File Island Echoes 버전업 프롬프트

이 디렉터리는 다른 Codex 세션에 전달할 기능 확장 및 버그 수정 프롬프트를 버전별로 관리한다. 제품 버전은 `package.json`의 SemVer와 맞춘다.

- 기능 버전: `v<major>.<minor>-<slug>.md` (예: `v0.6-new-feature.md`)
- 버그 수정 버전: `v<major>.<minor>.<patch>-<slug>.md` (예: `v0.6.1-save-fix.md`)

현재 제품 버전은 `0.8.2`이며 v0.8.2까지 완료되었다. 다음 작업은 v0.9 모바일 PWA이며, 이어서 v0.9.1 대상 링·이야기 선택 patch를 완료한 뒤 v0.10 버그 신고 기능으로 넘어간다. 새 기능 요청은 별도 지시가 없으면 v0.11부터 배정한다. 완료되었거나 작업 중인 기능 버전에서 발견된 버그는 기능 프롬프트에 합치지 않고 해당 기능 번호 아래의 다음 patch 버전으로 배정한다.

예를 들어 v0.6 구현 중 버그가 발견되면 `v0.6.1-<fix-name>.md`를 만든다. v0.6 구현 작업을 정리한 다음 v0.7로 넘어가기 전에 v0.6.1을 실행한다. 추가 수정이 필요하면 v0.6.2, v0.6.3 순으로 이어간다. 패치 번호를 사용해도 다음 기능 번호는 그대로 v0.7이다.

## 기능 프롬프트를 기록하는 규칙

새로운 기능 요청을 받으면 다음 순서로 관리한다.

1. 이 표에서 아직 사용하지 않은 다음 minor 버전을 고른다.
2. `v0.6-기능명.md`처럼 새 문서를 만든다.
3. 문서 상단에 상태, 선행 버전, 목표와 범위를 기록한다.
4. 다른 세션이 대화 기록 없이 실행할 수 있는 완결된 프롬프트를 넣는다.
5. 기존 기능과 저장 데이터에 미치는 영향, 검증 방법과 완료 조건을 포함한다.
6. 기능 구현이 끝났지만 별도 patch가 예정되어 있다면 상태를 `구현 완료 · 패치 예정`으로 기록한다.
7. 기능과 예정된 patch가 모두 실제로 완료되면 상태를 `완료`로 바꾸고 구현 기준 커밋 또는 검증 문서를 기록한다.
8. `package.json`과 사용자에게 표시되는 버전이 있다면 해당 릴리스 버전으로 맞춘다.

## 버그 수정 프롬프트를 기록하는 규칙

버그 수정은 사소해 보여도 별도의 patch 문서로 기록한다.

1. 버그가 발생한 현재 기능 버전을 기준으로 다음 patch 번호를 고른다.
2. v0.6에 patch가 없다면 `v0.6.1-<fix-name>.md`를 만든다. 이미 v0.6.1이 있으면 v0.6.2를 만든다.
3. 증상, 재현 절차, 기대 동작, 관찰된 동작, 영향 범위와 회귀 위험을 기록한다.
4. 원인이 아직 확인되지 않았다면 추측을 확정 사실처럼 쓰지 않고 진단 절차를 프롬프트에 포함한다.
5. 가장 작은 정당한 수정 범위를 사용하고 관련 없는 기능 확장을 patch에 섞지 않는다.
6. 자동 회귀 검사와 실제 사용자 경로 검증을 포함한다.
7. 선행 버전은 기반 기능 버전 또는 직전 patch로 지정한다. v0.6.2의 선행 버전은 v0.6.1이다.
8. patch 완료 시 `package.json`과 사용자에게 표시되는 버전을 `0.6.1`처럼 정확히 맞춘다.
9. patch가 완료되기 전에는 다음 기능 버전인 v0.7을 시작하지 않는다.
10. 전투 UI patch에서는 사용자가 요청하지 않은 상시 설명, 반복 튜토리얼 배너나 홍보성 문구를 임의로 추가하지 않는다. 조작 설명은 도움말에 통합하고 전투 화면에는 판단과 조작에 필요한 정보만 둔다.

문구 오탈자처럼 실행 동작에 영향이 없는 변경도 사용자가 버그 수정으로 요청하면 같은 규칙을 적용한다. 아직 구현하지 않은 기능의 요구사항 변경은 별도의 버그 수정이 아니라 해당 예정 기능 프롬프트를 갱신한다.

## 여러 버전을 순차 실행하는 방법

사용자가 다른 세션에서 다음과 같이 요청할 수 있다.

> `docs/version-prompts/README.md`를 읽고 v0.6부터 v0.7까지 순차적으로 진행해줘.

이를 받은 세션은 다음 규칙을 따른다.

1. 지정 범위의 기능 및 patch 프롬프트 파일이 모두 존재하는지 확인한다.
2. 버전을 숫자 순서로 정렬한다. 문자열 순서가 아니라 `v0.6 → v0.6.1 → v0.6.2 → v0.7` 순서다.
3. v0.6의 선행 조건을 확인하고 프롬프트 전체를 구현한다.
4. v0.6의 구현, 테스트, 빌드, 실제 브라우저 검증과 문서 갱신을 마친다.
5. v0.6.1 문서가 있으면 v0.7보다 먼저 구현하고 검증한다. v0.6.2 등 추가 patch도 모두 같은 방식으로 처리한다.
6. 해당 기능 버전의 모든 patch가 완료된 후에만 다음 기능 버전으로 넘어간다.
7. 실행 도중 새 버그가 발견되어 patch 문서가 추가되면 현재 기능 버전 작업 직후 실행 대기열에 삽입한다.
8. 후속 버전 때문에 이전 버전의 요구사항이 깨지면 관련 버전을 완료된 것으로 처리하지 않는다.
9. 각 기능 및 patch 버전의 완료 여부와 검증 결과를 버전별로 구분해 보고한다.

따라서 “v0.6부터 v0.8까지 순차 진행”은 다음처럼 해석한다.

```text
v0.6
→ 존재하는 모든 v0.6.x patch
→ v0.7
→ 존재하는 모든 v0.7.x patch
→ v0.8
→ 존재하는 모든 v0.8.x patch
```

지정한 프롬프트 파일이 아직 없으면 기능을 임의로 추측하지 않고 누락된 버전과 필요한 요구사항을 사용자에게 알린다. 프롬프트가 `초안` 상태라면 구현할 수 있지만, 불명확한 핵심 결정이 있으면 기존 코드와 문서에서 먼저 근거를 찾는다.
