# v0.5.1 — 터치 효과음 지연 수정

- 상태: 완료
- 유형: 버그 수정
- 선행 버전: v0.5
- 제품 버전: `0.5.1`
- 작성일: 2026-09-10

## 증상

모바일 또는 터치 입력으로 버튼과 카드를 조작하면 시각적 반응보다 효과음이 약 0.5초 늦게 들린다. 게임 로직은 반응하지만 소리가 손가락 입력에 붙지 않아 조작감이 둔하게 느껴진다.

## 재현 절차

1. 실제 모바일 기기 또는 터치 입력이 가능한 브라우저에서 배포 사이트나 프로덕션 빌드를 연다.
2. 타이틀에서 소리를 활성화한다.
3. 캐릭터 선택, 지도 노드, 카드 선택, 턴 종료와 설정 버튼을 각각 터치한다.
4. 손가락이 화면에 닿거나 버튼이 시각적으로 반응한 시점과 효과음 시작 시점의 차이를 확인한다.
5. 각 효과음을 처음 재생하는 냉상태와 이미 한 번 재생한 캐시 상태를 나누어 비교한다.
6. 마우스 클릭과 키보드 Enter/Space에서도 같은 지연이 있는지 비교한다.

## 기대 동작

- 자주 사용하는 UI 및 카드 선택 효과음은 터치의 시각적 반응과 거의 동시에 시작한다.
- 캐시가 준비된 효과음은 입력 이벤트부터 Web Audio 재생 예약까지 50ms 이내를 목표로 한다.
- 실제 청감상 일반 입력 효과음은 가능하면 100ms 이내에 들려야 한다.
- 첫 오디오 활성화, 포맷 디코딩 또는 운영체제 출력 지연처럼 앱이 완전히 통제할 수 없는 시간은 별도로 측정하고 보고한다.
- 음악, 진화 징글과 의도적으로 순서를 맞춘 전투 효과의 연출 지연은 유지할 수 있지만, 그 지연은 입력 확인음과 구분되어야 한다.

## 현재 동작에서 확인할 지점

현재 코드에는 다음과 같은 잠재적 지연 지점이 있다. 이는 확정된 원인이 아니며 실제 계측으로 구분해야 한다.

- `src/main.ts`의 정상 버튼 효과음은 `pointerdown`이 아니라 `click` 처리에서 요청된다.
- `pointerdown`에서는 AudioContext 해제와 비활성 버튼 효과음만 처리한다.
- 클릭 처리에서 `unlock()`을 기다리지 않고 `gameAudio.action()`을 연달아 호출한다.
- `AudioManager.play()`는 캐시에 없는 큐를 재생할 때 `fetch`와 `decodeAudioData` 완료를 기다린다.
- v0.5는 필요한 파일을 처음 사용할 때 지연 로드하므로 새로운 종류의 효과음마다 냉상태 지연이 발생할 수 있다.
- `transitionCues()`에는 연출 순서를 위한 0.06~0.5초 지연이 의도적으로 포함되어 있다.
- 오디오 파일 자체의 앞부분 무음, 코덱별 디코딩 차이, AudioContext의 출력 latency도 다시 확인해야 한다.

```text
현재 저장소의 File Island Echoes v0.5에서 실제 터치 시 효과음이 시각적 반응보다 약 0.5초 늦게 들리는 문제를 v0.5.1 patch로 진단하고 수정해줘.

먼저 AGENTS.md, docs/version-prompts/README.md, docs/version-prompts/v0.5-audio.md, AUDIO.md, VALIDATION.md와 현재 Git 상태를 확인한다. 기존 사용자 변경사항을 보존하고 관련 없는 게임 규칙이나 콘텐츠를 변경하지 않는다.

증상:
- 모바일 또는 터치 입력에서 버튼, 카드와 지도 노드를 누르면 효과음이 약 0.5초 뒤에 들린다.
- 화면과 게임 상태는 먼저 반응하지만 소리가 입력에 붙지 않는 느낌이 난다.

먼저 다음 경우를 분리해 재현하고 시간을 계측한다.
- 오디오를 처음 활성화하는 첫 터치
- 특정 효과음을 처음 사용하는 냉상태
- 같은 효과음이 이미 디코딩된 캐시 상태
- pointerdown, pointerup과 click 사이의 이벤트 시간
- 이벤트 발생부터 AudioBufferSourceNode.start() 호출까지의 시간
- start 예약 시각과 AudioContext.currentTime의 차이
- 의도적인 transitionCues delay
- OGG와 MP3 파일 앞부분의 무음 및 디코딩 차이
- AudioContext.baseLatency/outputLatency를 지원하는 브라우저의 출력 지연
- 마우스, 키보드와 실제 터치 입력의 차이

개발 모드에서만 사용할 수 있는 계측 수단을 추가해 입력 시각, 큐 ID, 캐시 적중 여부, 로드·디코딩 시간과 source.start 예약 시각을 기록해도 된다. 프로덕션 콘솔에 반복 로그를 남기거나 사용자 입력 정보를 수집해서는 안 된다.

현재 구조에서 특히 다음을 확인한다.
- src/main.ts는 정상 버튼의 gameAudio.action()을 click에서 호출하며 pointerdown은 unlock과 비활성 버튼에만 사용한다.
- click 처리에서 unlock()은 await하지 않고 action 재생을 즉시 요청한다.
- AudioManager.play()는 캐시에 없는 파일에 대해 fetch와 decodeAudioData를 기다린다.
- transitionCues()의 일부 효과는 연출을 위해 0.06~0.5초 뒤에 예약된다.

계측 결과에 따라 원인을 수정한다. 아래 방식을 무조건 모두 적용하지 말고 확인된 지연에 필요한 조합만 사용한다.

1. 첫 오디오 활성화 직후 자주 쓰는 작은 효과음을 우선 준비한다.
   - ui-confirm, ui-select, ui-cancel, ui-denied, card-select, card-attack, card-guard, card-support, node-select를 우선 대상으로 검토한다.
   - 음악보다 작은 UI 효과음의 fetch와 decode를 우선한다.
   - 한꺼번에 모든 징글과 음악을 디코딩하지 않는다.
   - 준비 작업은 게임 진행이나 첫 화면 렌더링을 막지 않는다.

2. AudioContext 생성 옵션에 latencyHint: 'interactive'가 실제 대상 브라우저에서 도움이 되는지 확인한다.
   - 타입 호환성과 webkitAudioContext 대체 경로를 유지한다.
   - 지원하지 않는 브라우저에서는 기존처럼 정상 생성되어야 한다.

3. 터치 이벤트 자체가 원인이면 입력 확인음을 가능한 이른 이벤트에서 재생한다.
   - pointerdown에서 소리를 재생하고 click에서 게임 동작을 수행하는 방식을 검토한다.
   - 동일 동작의 pointerdown과 후속 click에서 효과음이 두 번 나지 않도록 명시적으로 중복 제거한다.
   - 손가락 스크롤, 포인터 취소, 다른 요소로 이동한 경우 잘못된 확인음이 나지 않는지도 고려한다.
   - 키보드 Enter/Space와 보조기기에서 발생하는 click에는 동일한 효과음이 한 번 재생되어야 한다.
   - 비활성 카드의 energy-low/ui-denied 처리도 중복되지 않아야 한다.

4. 캐시 미스가 원인이면 AudioManager에 작은 우선 프리로드 API를 추가한다.
   - 동일 큐의 중복 fetch/decode를 만들지 않는다.
   - 기존 pending, buffers, failed, 동시 음성 제한과 캐시 정책을 재사용한다.
   - 프리로드 실패는 게임을 막지 않고 실제 재생 시 대체 포맷을 다시 시도할 수 있게 설계한다.
   - 배경음악 세 곡 캐시 제한과 효과음 캐시를 서로 잘못 제거하지 않는다.

5. 첫 입력만 구조적으로 늦는다면 첫 터치와 이후 터치를 구분한다.
   - 자동재생 정책을 우회하지 않는다.
   - 사용자 입력 없이 소리를 재생하지 않는다.
   - 오디오 활성화 버튼 자체에는 즉시 들리는 짧은 피드백을 제공할 수 있는지 검토한다.
   - 이를 위해 v0.5의 “첫 입력 전 오디오 요청 없음” 정책을 변경해야 한다면, 자동재생과 개인정보 보호에는 영향이 없고 초기 전송량 변화가 작은지 확인한 뒤 AUDIO.md에 변경 이유와 수치를 기록한다.

6. transitionCues의 지연은 입력 확인음과 전투 결과음을 분리해서 판단한다.
   - card-select나 ui-confirm은 즉시 재생한다.
   - 타격, 상태 적용, 적 행동과 같은 결과음은 실제 화면 애니메이션에 맞춘 지연을 유지하거나 재조정한다.
   - 모든 delay 값을 일괄 0으로 바꾸지 않는다.

성능 목표:
- 디코딩된 UI 효과음은 입력 이벤트에서 source.start() 예약까지 50ms 이내를 목표로 한다.
- 일반적인 실제 청감 반응은 가능하면 100ms 이내를 목표로 한다.
- 냉상태와 첫 활성화는 별도 수치로 기록한다.
- 작은 우선 프리로드로 늘어난 초기 네트워크 용량과 메모리 사용량을 측정한다.
- 기존 전체 오디오 약 15MiB 예산과 지연 로딩 원칙을 유지한다.

회귀 검사를 추가한다.

- 우선 프리로드는 같은 큐를 중복 디코딩하지 않는다.
- 빠른 pointerdown/click 조합에서 효과음은 한 번만 재생된다.
- 키보드 click에서도 효과음이 한 번 재생된다.
- 비활성 카드와 에너지 부족음이 중복되지 않는다.
- 음악 전환, 징글 덕킹, 동시 음성 제한, 음소거와 볼륨 저장이 유지된다.
- 백그라운드 복귀 후 첫 터치에서도 중복 AudioContext나 중복 음악이 생기지 않는다.
- 오디오 로드 실패 시 게임은 계속 동작한다.
```

## 완료 조건

- 지연의 원인이 이벤트, unlock, fetch/decode, 의도적 delay 또는 출력 latency 중 어디에 있는지 증거와 함께 기록된다.
- 캐시가 준비된 일반 UI 효과음의 앱 내부 예약 지연이 목표 범위 안에 든다.
- 첫 활성화와 처음 쓰는 큐의 지연이 기존보다 줄고 측정값이 남는다.
- 터치, 마우스와 키보드에서 효과음이 정확히 한 번 재생된다.
- 카드 결과음과 전투 연출음의 순서가 깨지지 않는다.
- 음소거, 볼륨, 음악, 징글, 백그라운드 복귀와 로드 실패 처리가 회귀하지 않는다.
- 자동 테스트, 오디오 감사, 프로덕션 빌드와 Pages 검사가 통과한다.
- 제품 버전은 `0.5.1`이고 기존 저장은 유지된다.
